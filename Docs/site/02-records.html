What goes into a record?

On the shape of what an app files, and what the index makes of it.

The playground, step 2 · the playground

A record is a value the app already has, plus a little schema. The playground's is a harbour log entry: an id, a title, the text, and a couple of tags.

AII files each value as a record. The value travels inside an envelope that names the app, the kind, the id and the group. The text is cut into partitions, pieces of about 1,500 characters, and each one is embedded on its own. A short entry like the harbour's is a single partition.

Tags matter more than they look. Any tag turns off the index's own entity extraction and becomes the record's entity instead. Search looks through entities before it ranks anything, so a tag is the surest way for a record to be found.

A question in plain words, “Who looks after the lighthouse?”, found nothing. That gap is where the next chapter starts.

What makes a good record

The harbour log was written to show provenance plainly, and its habits carry over to any experiment.

  • One paragraph per entry, so each entry is one partition.
  • A distinct opening. Each entry names its subject first and its fact second, and no two share a sentence template. Retrieval matches templates more readily than names.
  • Tags on every entry. They keep extraction off, and they are what search finds.
  • Invented facts. The base model cannot know them, so every token that states one shows which source supplied it.
  • Enough text. The whole log must fill more than one training window.

Edit an entry and run again, and the Thread trains on from where it was and a new version goes live. Delete one and it stays in the lane, because remembering never removes; run.sh forget clears the group.

For model engineers: the protocol, the envelope, the chunker

AIIRecordable asks for a kind, a group, an id, a title and the text; everything else has a default. The id on the wire is <app>/<kind>/<recordID>. The envelope is the canonical JSON of aii-record/1, and AII refuses one over 1 MB, so bulk text belongs in text, which becomes the partitions.

The chunker packs whole paragraphs up to about 1,500 characters, never more than 2,000; a longer paragraph is cut at sentence ends, and a longer sentence is cut hard. The record figure above runs a port of it, and checks it against what the Thread service stored for all 18 entries.

remember files every value, then reads the documents back until each one carries the envelope it just filed; it gives up with notReady after 15 seconds, often while the embedder loads. Re-remembering an id replaces it.

A record is the app's own value, filed whole. Its text is what a Thread will learn from.
